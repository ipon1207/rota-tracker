# コメント規約

詳細:

- [バックエンドコメント規約詳細.md](./BACKEND_COMMENT_GUIDE.md)
- [フロントエンドコメント規約詳細.md](./FRONTEND_COMMENT_GUIDE.md)

## 目的と前提

コメントは、コードを読まなくても意図が伝わるようにするための注釈

AIがコードを生成・レビューする前提のプロジェクトでは、コメントは人間だけでなく **AIが読む仕様** としても機能する

誤ったコメントはAIに誤った実装を生成させるため、コメントの誤りはコードの誤りと同等に扱う

- コメントはコードの一部である。PRのレビュー対象に含める
- 実装を変更したら、**同じPRでコメントも更新する**

### 人間とAIの分担

| 種別 | 内容 | 担当 |
| --- | --- | --- |
| 契約（What） | 要約、引数、戻り値、例外 | AIが下書き → 人間が修正 |
| 意図（Why） | 背景、制約、前提、却下した案 | **人間が書く** |

AIはリポジトリ内の情報しか持たないため、Whyを書かせると「呼び出し元の名前」など、コードから機械的に導ける事実を背景として出力する

これは本規約の禁止事項に該当する

- AIには `// WHY:` の空欄のみを置かせる
- 空欄が埋まっていないPRは、人間がレビュー時に埋める
- AIにWhyを書かせる場合は、Issue・仕様書など**リポジトリ外の材料をコンテキストとして渡すことを必須**とする

## コメント記述の判断基準

書くべきか迷ったら、この2つで判定する

1. **リポジトリを全部読めば書けてしまう内容か？** → YES なら書かない
2. **読み手の「消す / 変える / そのまま使う」の判断を変えるか？** → NO なら書かない

### 判定例

```ts
// NG: 1に抵触（呼び出し元はIDEの参照機能で辿れる）
// UserTable で使用するため

// OK: 2を満たす（削除の意思決定ができる）
// WHY: 2025年の暫定運用のために追加（2026年度の評価期間開始後は不要になる予定）
```

## MUST

1. **不可逆な決定は、コードの隣に制約として書く**

    永続化フォーマット、外部公開APIの契約、モジュール間の暗黙の前提、権限に関わる仕様
    「実装は簡単だが、リリース後に戻せない」箇所が対象。実装の難易度では判断しない

2. **public な export / public メンバーには契約コメントを書く**

    書式は各詳細規約に従う（TS: TSDoc / C#: XMLドキュメントコメント）

3. **静的解析で辿れない依存は書く**

    リフレクション、DI経由の解決、SQLの列名との一致、生成コードとの対応など

4. **lint・コンパイラの抑止には理由を併記する**

    `oxlint-disable` / `@ts-expect-error` / `#pragma warning disable` など

5. **実装を変更したら、同じPRでコメントを更新する**

## MUST NOT

1. **コードから自明な説明**
2. **IDEの参照機能で辿れる関係**
3. **実装手順（How）の逐次説明**
4. **型情報を文章で繰り返すこと**
5. **コメントアウトされたコードの放置**
6. **著者名・作成日・変更履歴**

## SHOULD

- タグは **`TODO` / `FIXME` / `HACK` / `NOTE` の4種のみ**を使う
  - `TODO`: 後で対応予定（**Issue / 仕様書 / DESIGN_NOTES への参照を添える（`@see` / `<see href="">`）**）
  - `FIXME`: 既知の問題・暫定対応
  - `HACK`: 望ましくないが必要な実装
  - `NOTE`: 設計上の理由・参考情報

## 決定の記録先

コード内のコメントは**短く契約だけを示し、詳細は外部に逃がす**

1. **PRの説明欄に書く**
2. **人間が** `docs/DESIGN_NOTES.md` に転記する

### DESIGN_NOTES.md の書式（1決定 = 5項目）

```markdown
## <対象>

- 決定:
- 却下した案と理由:
- 禁止事項:
- 影響範囲:
- 出典: #123
```

- **AIに生成させない**
- 5項目で書けない場合は、決定そのものが固まっていない可能性を疑う
- 空のテンプレートを先に置かない（埋めるためにAIに書かせる圧力が生まれるため）

## 強制の手段

| 対象 | 手段 | 初期設定 |
| --- | --- | --- |
| バックエンド | `GenerateDocumentationFile` による CS1591 警告 | 警告のまま運用 |
| フロントエンド | TSDoc形式で統一 | Oxlintのjsdoc系ルールの対応状況を確認のうえ導入 |
| 共通 | AIレビュー | 本書の MUST / MUST NOT をレビュー観点として渡す |

### AIレビューに渡す観点

- MUST / MUST NOT に違反していないか
- リポジトリ内から導ける内容が含まれていないか
- 不可逆な変更が含まれるのに、対応する記録（DESIGN_NOTES）がないか
- 実装が変更されたのにコメントが更新されていない箇所がないか
- MUSTの1つ目の項目に該当するが、`DESIGN_NOTES` に記述がないか

## 記述言語

- 要約・説明・背景は **日本語**で書く
- タグ名（`@param`, `<summary>` など）は英語のまま
- 識別子・型名・エラー名は原文のまま記載する
