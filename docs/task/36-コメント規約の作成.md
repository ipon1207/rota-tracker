## 意図・背景のコメント

```ts
/**
 * 万博の混雑時間を取得
 * 背景: 2025年大阪万博で利用するため（後続で削除予定）
 */
const getExpoCongestedTime = (targetDate: Date): Promise<Time[]> => {
  // ...
  return congestedTimeList;
}
```

- 「万博の混雑時間を取得」だけだと、長期運用されたときに誤解を生みかねない
- **特に深くコードを読む必要もなく、消す意思決定が上記の例ではできる**
- 何のため（仕様に近い）に実装したコードなのかを明記することが大切

→ AIにこのルールを適用した場合「●●funcitonで使用するため」のように書きかねない（繰り返しのアンチパターンが増える）
→ **リポジトリ内から読み取れる背景は「背景」ではない**
→ **AIに背景を書かせない**

## 仕様 / 契約のコメント (JsDoc / TsDoc)

```ts
/**
 * 万博の混雑時間を取得
 * 背景: 2025年大阪万博で利用する（後続で削除予定）
 * 
 * @param targetDate 混雑時間取得対象の日付
 * @return 混雑時間の配列
 */
const getExpoCongestedTime = (targetDate: Date): Promise<Time[]> => {
  // ...
  return congestedTimeList;
}
```

- JavaScript / TypeScriptでは関数が持っている性質や仕様、契約についてのコメント
- 全てに書く必要はないが、`utils` や `lib` のような多く参照される可能性があるものに書いてあるとよい

## 繰り返しを避ける

```ts
// 状態のコピーを取得する
const copyState = getCopy(state);

// copyStateがある場合
if (copyState) {
  // 新しい状態をコピーする
  newState = copyState;
} else {
  // 新しい状態をnullにする
  newState = null;
}
```

- コードから読み取れる情報以上のことが書いていない

## クロスモジュールコメント

```ts
export type DBStatus = 'pending' | 'running' | 'done';
```

DBにはintとして保存されるというコードからでは読み取れない仕様がある

```ts
export type DBStatus = 'pending' | 'running' | 'reject' | 'done';
```

```SQL
-- 0 = pending, 1 = running, 2 = done
INSERT INTO orders (
   id
  ,status
)
VALUES (
   123
  ,0
);
```

`'reject'` を途中に挟むと、既存の `done(2)` が `reject(2)` になってしまう

```ts
/**
 * NOTE:
 * - DB には数値 (0,1,2) として保存されるため、**順序を変えたり再割当てするのは禁止**
 * - 新しい状態は必ず末尾に追加する
 * - 内部的には string union だが、DB/外部APIでは int enum として扱われる
 * - 詳細は DESIGN_NOTES.md「DBStatus」参照
 */
export type DBStatus = 'pending' | 'running' | 'done' | 'reject';
```

```md
## DBStatus（Cross-module decision）

- 数値は外部永続化されるため途中挿入・再割当禁止。(**Append-only**)
- 既存コードは `status >= Running` のような数値比較に依存している。
- 追加手順:
  1. 新値は末尾に追加
  2. マイグレーションが必要か検討
  3. リリースノートに “enum append-only” を明記
```

- **コードのコメントは完結に契約に示す → 詳細は DESIGN_NOTES で深掘り**

→ AIに `.md` はあまり書かせたくない（冗長的な気がするから）
→ そもそも `DESIGN_NOTES` を書く実装は人間の領分では？（理由は説明できないが直感的に）

## 所感

- どんなものでも参照が増えると、やりにくく感じる
- AIが出力する文書・コメントは具体性を持たせようとして、順番付きの項目とか順番付き見出しを使って、それを文書内で参照させるから読みにくいものになる気がする
- 参照の仕方にも、うまいやり方があると思う
