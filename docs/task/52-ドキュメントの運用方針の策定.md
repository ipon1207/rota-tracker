# ドキュメントの運用方針の策定

## ドキュメントが持つ機能

### 合意（同時点・異なる立場の間）

発注者と開発者、部署Aと部署Bが「**同じもの思い浮かべている**」状態を作る

口頭の合意だと、双方の認識のずれが起こる可能性があるため、アウトプットして固定する必要がある

### 伝達（同じ立場・異なる時点の間）

半年後にプロジェクトに参画する人・3年後に保守する人、未来の自分に**伝える**

チームの人数が増えるほど、また時間軸が長いほど価値が上がる

### 思考（書く行為そのもの）

書くと矛盾が見つかる、曖昧な部分が浮き上がる

設計書を書いている途中で、気付きがある

成果物（ドキュメント）は副産物で、**成果物を作成する過程が機能そのものの役割になる**

### 検証基準（オラクル）

**「正しく動いている」を判定する**根拠

### 証拠・責任（監査・契約）

誰がいつ何を承認したか

#### V字モデルにあてはめた機能

| 工程 | 一番強い目的 | 二番目に強い目的 |
| --- | --- | --- |
| 要求分析 | 合意 | 思考 |
| 要件定義 | 合意 + 証拠 | 検証基準 |
| 基本設計 | 合意（機能レベル）+ 検証基準 | 伝達 |
| 詳細設計 | 思考 | 伝達 |
| コーディング | 伝達 | - |

上流は**合意と証拠**が主目的となり、ドキュメントは腐りにくい

下流は**思考と伝達**が主目的となり、現在の状態を扱うため、腐りやすい

## ここまでの内容の帰結

### 「書いた時点で役目を終える文書」がある

詳細設計書の主目的が思考なら、書き終わった瞬間に目的をほとんど果たすことができている

その後、保守されずに腐っても、損失は小さいはず...

むしろ、永続文書（を目的）として扱おうとすると「更新されていないのは、けしからん」という話になってしまう

**捨てる前提の文書と残す前提の文書を最初から分ける**ことが正解なのではないか？

### 一つの文書に複数の目的を詰め込むと必ず壊れる

例に要件定義書を上げると

- 発注者との合意文書（＝固めたい）
- 実装者へのインプット（＝最新化したい）
- 検証基準（＝テスト実施時点の実態と一致していてほしい）

という矛盾した要求となる

凍結すべき文書と追従すべき文書を一冊にまとめると壊れるということもある

↑ （単一責任の原則みたいだと思った）

### 目的が消えても文書だけが残る

目的もなく「ルール」として作成される設計書は、5つのどれにも該当しない場合がある

- 合意する相手がいない
- 伝達先がいない
- 検証にも使われれない

この場合、ドキュメントの作成コストは単純な損失となる

## 文書作成の際に考えるべき問い

新しい文書を作成するとき、自分自身で以下のように考えることが大切

> この文書は、**誰の**、**どの判断**を変えるのか

## ここまでの疑問

- 機能に即したドキュメントの具体的な形とはなんなのか
- V字モデルだけで話を進めたが、アジャイル・プロトタイプ・イテレーションなど一般的な開発に通用する話なのか
- コーディング過程で作成する文書はまたレイヤーが違うのではないのか（環境構築手順、技術スタック選定、

## 一般化した場合

> 開発手法は「5つの機能をどの媒体に割り当てるか」の設計
>
> 機能そのものは消えない
>
> 消えるのは、その機能が不要な文脈

媒体の候補となるものは文書だけではない

- 合意：文書 / 会話 / 動くもの / テスト
- 伝達：文書 / 口伝 / コード / テスト
- 思考：文書 / 図 / 試作 / 実験
- 検証基準：仕様書 / 自動テスト / ユーザー反応
- 証拠：承認文書 / チケット履歴 / コミット

### 媒体が変わると腐りやすさも変わる

自動テストは壊れる教えてくれる、口伝は人が辞めると即座に消える

動くものは常に最新だが「なぜ」という情報を保持することができない

## コーディングという過程に焦点を当てて

| 腐敗の形 | 対処方法 | 例 |
| --- | --- | --- |
| 実態と重複している | 実態から自動生成 | パッケージ管理ファイル・DBスキーマ |
| 手続きを記述している | 実行可能にする | 手順書 |
| 過去の判断を基準にしている | 追記型にする | ADR |
| 契約を記述している | テストにする | API仕様 |
| どれにも当てはまらない | 要らない可能性が高い | |

## 腐敗を決める3つの要素

- 記述対象がどれくらいの速さで変化するのか
- その情報が他の場所にも重複して存在しているか
- 実態と乖離したときに気付くことができるか

| | 要件定義書 | 詳細設計書 | ADR | 技術スタック一覧 |
| --- | --- | --- | --- | --- |
| 変化速度 | 遅い | 速い | 変わらない（過去の記録のため） | 中 |
| 重複対象 | 無し | コード | 無し | パッケージ管理ファイル |
| 結果 | 腐りにくい | 腐りやすい | 腐りにくい | 腐りやすい |

## ドキュメントの「機能」と「腐敗の形」の関係

ドキュメントの腐敗を直接決めるのは後者

前者は腐敗の原因ではなく、**腐ったときの被害の大きさ**と、**捨ててよいかどうか**を決める

| 文書 | 腐敗の形 | 機能 | 腐る頻度 | 被害 |
| --- | --- | --- | --- | --- |
| ADR | 過去の判断 | 証拠・伝達 | ゼロ | - |
| 詳細設計書 | 実態と重複 | 思考 | 高い | 小さい |
| API仕様 | 契約 | 合意・検証基準 | 中 | 大きい |
| 環境構築手順 | 手続き | 伝達 | 最高 | 大きい |
| ルールとして作成した設計書 | 該当無し | 該当無し | - | （作成する必要がない） |

### 診断結果

- `docs/task`・`docs/spike` は各タスクの学習ログで健全（問題なし）
- [COMMENT_GUIDE](../COMMENT_GUIDE.md)・[BACKEND_API_GUIDE](../BACKEND_API_GUIDE.md) はルール州で書かれていて、モジュール名の一覧ではなく判断基準で書いているため、腐りにくくなっている
- [BACKEND_ARCHITECTURE](../BACKEND_ARCHITECTURE.md)・[FRONTEND_ARCHITECTURE](../FRONTEND_ARCHITECTURE.md) はルール部分は良質だが、実態と食い違う部分がある
- [README](../../README.md) の「学習ログリンク」がズレている
- [COMMMENT_GUIDE](../COMMENT_GUIDE.md) は決定の記録先として、`docs/DESIGN_NOTES.md` がない
- [車輪の再発明トラッカー_移植設計](../../車輪の再発明トラッカー_移植設計.md) は移植初期のスコープ文書で、思考の道具として役目を終えているため、乖離を直す大砲ではない
